# M3.2 REPORT — the fp32 recovery experiment (xp-005)

A single controlled paid run testing **one** causal hypothesis. Authorized: one fp32 retrain,
hard cap A$1.00. Result: **the hypothesis is refuted** — fp32 does not fix the collapse, and it
did so with *stable* gradients, which is the interesting part.

## Hypothesis

> The M3/M3.1 training collapse to a constant output (docs/M4-REPORT.md) was caused **primarily
> by bf16 instability** in this DeBERTa-v3-base fine-tuning setup.

M4 flagged bf16 because the failed runs showed gradient-norm spikes (~70 against a clip of 1.0)
and the training literature recommends fp32 for DeBERTa. M3.2 tests that directly.

## Controlled delta from M3.1

M3.2 (`xp-005`) is byte-identical to M3.1 (`xp-004`) in every result-affecting field **except
precision**. The experiment fingerprint diff confirms it — the only change is one field:

```
xp-004  pl1:8c9a5517…   training.precision = bf16
xp-005  pl1:04857dd3…   training.precision = fp32   <- the sole intentional change
```

Same model + revision, tokenizer, manifests (all three sha256 matched the approved fingerprint
at start, on the pod), seed, LR/scheduler/warmup/weight-decay/epochs/grad-clip, pauc checkpoint
selection, calibration, success bar. Any change in outcome is attributable to precision alone.

## Training stability

Loss falls **smoothly and monotonically** — no oscillation, no divergence:

| update | epoch | train_loss | grad_norm | val_score_std | val_n_unique | val_class_sep | collapsed |
|--:|--:|--:|--:|--:|--:|--:|:--:|
| 100 | 0 | 0.7138 | 6.27 | 4.9e-05 | 2 | 1e-06 | **yes** |
| 200 | 0 | 0.7055 | 1.03 | 0.0 | **1** | 0.0 | **yes** |
| 300 | 0 | 0.6941 | 0.35 | 0.0 | **1** | 0.0 | **yes** |
| 400 | 1 | 0.6801 | 0.81 | 1.2e-04 | 2 | 0.0 | **yes** |

The loss converges toward **0.688** — exactly the cross-entropy of the *optimal constant
predictor* at the class base rate (positives 0.457). The model is minimizing loss by learning the
**bias and nothing input-dependent**.

## Gradient behavior

**This is the decisive evidence.** Max gradient norm over the whole run was **8.87**; per-eval
norms were 6.27 → 1.03 → 0.35 → 0.81. No spikes, no NaN/Inf (`nonfinite_encountered = false`).
Contrast with the bf16 runs, whose grad norms spiked to ~70 — the very instability the hypothesis
blamed. **fp32 removed the gradient instability and the model collapsed anyway.**

## Collapse diagnostics

The pre-registered runtime gate (score std < 1e-3, or < 2 unique scores, or class separation
< 1e-3; warmup 3 evals, patience 3) fired at update 400 after **4 consecutive collapsed
checkpoints** — including two (updates 200, 300) with a **literal single distinct score** across
all 1,644 validation pairs. `stop_reason`: *sustained collapse … class separation 0.00e+00*. The
gate did its job: it terminated a doomed paid run in <1 minute instead of burning the full 4
epochs.

## Validation performance

operating point separates the classes). Constant scores ⇒ no discrimination.

## Root-cause verdict

**bf16 instability is NOT supported as the dominant cause of the collapse.** Under the otherwise
matched M3.1/M3.2 setup, fp32 training produced **stable gradients (max norm 8.87, no spikes) and
a smoothly decreasing loss, yet collapsed to a constant output identically to bf16.** The M4
gradient-norm spikes were a *symptom* co-occurring with bf16, not the driver of the collapse. The
cause is **precision-independent** and lies elsewhere — most plausibly the optimization/objective
setup for this model (learning rate / warmup / schedule; DeBERTa-v3 is known to be sensitive) or
the input→[CLS]→head signal path, not numerical precision.

*Careful phrasing (this is one model/config/run):* fp32 did not rescue the run **within the
pre-registered collapse gate (through the end of epoch 1)**. Whether an ungated full-4-epoch fp32
run would eventually escape the base-rate basin was not observed; the constant output and zero
class separation sustained across a full epoch make a late recovery unlikely, but it is not
strictly excluded by this experiment.

## Scientific disposition

**`FP32_HYPOTHESIS_NOT_SUFFICIENT`.**

Per the pre-registered ladder, M3.2 failed **Level 0 (training mechanics)** — the model is
demonstrably collapsed — so its low-FP numbers are **not** a model-quality verdict and are not
interpreted as one. (The keyless report's generic signal reads `REGRESSION`, reflecting only that
a collapsed model scores below NLI; the governing M3.2 disposition is the Level-0 mechanics
failure above.)

## Next decision

**No further paid run without a $0 diagnostic first.** M3.2 has redirected the investigation:
the collapse is not about precision, so the next step is a **free, local** root-cause pass, e.g.:

1. **Overfit-one-batch** on CPU (a handful of pairs, many steps): a correct setup memorizes them.
   If it *can't*, the bug is in the objective/label/encoding wiring, not the data or precision.
2. **Signal-path sanity**: confirm the [CLS]/ContextPooler output *varies with input* pre-head,
   and that both classes' labels reach the loss (the head-index convention).
3. **Optimization**: a short LR/warmup probe (e.g. 1e-5, longer warmup, or layer-wise decay) —
   DeBERTa-v3 fine-tunes are LR-sensitive; 2e-5 may sit outside its stable basin here.

Only if a $0 diagnostic identifies a concrete fix would a further paid run be proposed, with its
own cost packet and owner approval. Portfolio/résumé remain untouched (a collapsed model is not a
result to show).
